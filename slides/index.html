Today: dbplyr for R and ibis for Python. Same idea in both: write dataframe code, the warehouse runs it. The same packages and Posit integrations work with other cloud platforms such as Snowflake.

Recommend SQL warehouses as the default for analysts. Spark is for when you genuinely need distributed compute. dbplyr and ibis both translate dataframe code to SQL, so analysts don't have to switch languages to use the warehouse.
02 · Credentials

Best practice 1: no credentials in code

One line of code. It authenticates correctly everywhere.

# R
con <- dbConnect(
  odbc::databricks(),
  httpPath = Sys.getenv("DATABRICKS_HTTP_PATH")
)

# Python (ibis)
cfg = databricks_config(
  posit_workbench_strategy=WorkbenchStrategy(),
  posit_connect_strategy=ConnectStrategy(),
  posit_default_strategy=databricks_cli,
)
Where it runsWho Databricks sees
WorkbenchYou, via managed credentials from your sign-in
Connect: appEach viewer, via an OAuth integration
Connect: scheduleA named service account
LaptopYou, via databricks auth login

Avoid: personal access tokens in scripts or .Renviron, and one shared login behind every app.

This is the single most important slide for a regulated environment. Tokens are short-lived and minted from SSO, so there's nothing to leak, rotate, or revoke when someone leaves. Audit logs in Databricks show the real person.
02 · Performance

Best practice 2: let the warehouse do the work

cases <- tbl(con, I("catalog.schema.table"))

cases |>
  filter(disease == "Coccidioidomycosis") |>
  summarise(cases = sum(cases), .by = county) |>
  show_query()   # see the SQL
  # collect()    # bring back ~58 rows
  • Tables stay lazy until you call collect() (R) or to_pandas() (Python)
  • Filter and aggregate first, then collect the small result
  • Check the SQL with show_query() or ibis.to_sql()
  • Use Databricks SQL functions directly when you need them

In today's demo the table has 199,125 rows. The dashboard never brings back more than about 60 at a time.

200k rows in our demo table; the app never pulls more than ~60. This is what keeps Shiny apps responsive and keeps sensitive line-level data out of R sessions.
02 · Access

Best practice 3: govern the data, not every app

Unity Catalog rules apply to whoever runs the query, in any tool

-- Small-cell suppression as a column mask
CREATE FUNCTION mask_small_cells(cases INT)
RETURN CASE
  WHEN is_member('phi_unmasked') THEN cases
  WHEN cases BETWEEN 1 AND 10 THEN NULL
  ELSE cases
END;

ALTER TABLE infectious_disease_cases
  ALTER COLUMN cases SET MASK mask_small_cells;
  • Grants on catalogs, schemas, and tables
  • Row filters such as county or program assignment
  • Column masks for suppression and PII
  • Lineage and audit for every query, from every tool
Our demo data is already public, but we've simulated the kind of de-identification rule you'd apply to sensitive data. Rates are masked too: a rate times the population gives you the count back. The point: write the rule once in the platform, and every Shiny app, report, notebook, and SQL query respects it automatically.

03 · Trustworthy AI

An AI agent you can check

Commons, from Posit, puts your trusted code at the center

Verified

Trusted calculation

The agent runs a measure taken from code you already trust, such as this dashboard and report.

Cited

New code with sources

The agent writes new SQL and cites the documentation that supports it.

Untrusted

Flagged for review

No trusted code or supporting documentation. The answer says so.

Labels come from the path the agent takes, not from the model. The model is Claude, served by Databricks, and every query runs as the viewer.

Commons is open source (R, and Python in beta). The agent's measures come from the dashboard, the report, and the R walkthrough; its dictionary and context come from CDPH's own published data dictionary. Because it uses the same per-session Databricks connection, the small-cell masks apply to the agent too. It mentions suppressed counties in its answers. No external API key: the LLM is a Databricks serving endpoint, authorized with the same viewer token.

The scheduled report in the repo (reports/disease-snapshot.qmd) uses the service account pattern. The service account's permissions define what every recipient can see, so scope it to the audience.
